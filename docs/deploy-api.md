# Deploying the SentinelOps API

Status: **deployed** on Render (https://sentinelops-ai-lukk.onrender.com) with Neon Postgres. The container image is built by CI
(`.github/workflows/ci.yml`). For a local stack with its own Postgres: `docker compose up --build` at the repository root.

## Steps (Render, free tier)

1. **Database.** Use a Postgres connection string (for example a Neon branch or database separate from the shop's). The API creates
   its own tables on first start (`events`, `incidents`, `hypotheses`, `evidence`, `diagnostic_runs`, `recovery_contracts`,
   `contract_transitions`, `approvals`, `action_runs`, `verification_runs`, `rehearsal_runs`, `rollback_runs`, `operators`,
   `incident_labels`, `prevention_artifacts`). New tables are added to an existing database on the next start. It never
   touches the shop's `orders` table.
2. **Create the service.** In Render choose New > Blueprint, select this repository, and apply `render.yaml`. Set:
   - `SENTINEL_DATABASE_URL`: the Postgres URL (`postgresql://` or `postgres://` both work).
   - `SENTINEL_INGEST_TOKEN`: a long random secret (`openssl rand -hex 24`). This is the **machine** credential: the shop's
     telemetry push and automation may ingest, read and run analysis with it, but never label, propose, approve or execute.
   - `SENTINEL_SESSION_SECRET`: generated by the blueprint. Without it nobody can sign in.
   - `SENTINEL_BOOTSTRAP_ADMIN`: `admin:<a password of 12+ characters>`. It creates the first admin only while no operator exists;
     remove it after the first sign-in.
3. **Check it.** `https://<service>.onrender.com/health` returns `{"status":"ok"}`. Open `/ui/` and sign in as the admin.
   Create the people who will use it (`POST /api/v1/operators` with `username`, `password`, `role`): `viewer` reads,
   `responder` analyses, labels, proposes and executes, `approver` also approves contracts and prevention artifacts, `admin`
   also manages operators. Four eyes still applies: nobody approves their own contract. For the campaign runner, create a
   `responder` named `campaign`.
4. **Connect the shop.** In the shop's Vercel project set `SENTINEL_INGEST_URL=https://<service>.onrender.com` and
   `SENTINEL_INGEST_TOKEN=<the same secret>`, then redeploy.
5. **Analyze.** Incidents appear when you press "Analyze now" in the dashboard (or `POST /api/v1/incidents/analyze`). To do it
   automatically set `SENTINEL_ANALYZE_INTERVAL_SECONDS=60` (not on serverless hosts, which cannot keep a background task alive).

## Known limits to accept before relying on it

- **Free instances sleep.** The shop gives up on a push after 3 s and drops the events, so telemetry sent while the API is
  waking up is lost. Use a paid instance or a keep-alive if that matters.
- **Retention is on by default (7 days)** but only runs when the periodic job is enabled (`SENTINEL_ANALYZE_INTERVAL_SECONDS` > 0) or when you call `POST /api/v1/maintenance/purge`. Events cited by evidence are kept.
- **Schema changes are not migrated.** `create_all` only creates missing tables. Changing a column needs a real migration
  (Alembic); until then drop and recreate the SentinelOps tables.
- **Sessions are stateless signed tokens** (8 hours by default). Sign-out, a password change or disabling an operator revokes
  every session of that operator at once. Five failed sign-ins lock a username for 15 minutes, counted per instance.
- **One tenant.** All operators see all incidents. There is no single sign-on (OIDC) yet: accounts are local to SentinelOps.
- **Upgrading from the shared-token version:** the default `SENTINEL_AUTH_MODE=operators` turns the old "token + your name" login
  off. Set `SENTINEL_BOOTSTRAP_ADMIN` before deploying, The old shared-token behaviour cannot be used on Render: it starts only
  with `SENTINEL_ALLOW_INSECURE_SHARED_TOKEN=true` and never when `RENDER` is set.
- **Executor is `mock`.** Approving and "executing" only records the action. `shop_admin` needs `SENTINEL_SHOP_ADMIN_URL` and
  `SENTINEL_SHOP_ADMIN_TOKEN` and changes the demo shop's fault state, so use it only against a demo shop.
- **No rate limiting** on the API apart from the sign-in lockout.
